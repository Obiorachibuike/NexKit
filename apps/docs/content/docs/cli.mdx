# CLI

`@nexkitjs/cli` installs the `nexkit` command. It scaffolds configuration and framework
wiring, keeps `.env.example` in sync with your schema, and diagnoses common setup problems.
Everything it generates is **plain TypeScript you own** — no runtime dependency on the CLI.

```bash
npx @nexkitjs/cli --help        # one-off
npm install -D @nexkitjs/cli    # or add it to the project
npx nexkit --help
```

## `nexkit init`

```bash
nexkit init [--framework express|fastify|none] [--dir src] [--force] [--dry-run]
```

Creates:

| File                 | Content                                                                                 |
| -------------------- | --------------------------------------------------------------------------------------- |
| `src/config/env.ts`  | `envSchema`, `Env` type and validated `env` using `@nexkitjs/config`                     |
| `src/nexkit.ts`      | `createNexkit(options)` wiring logger, health registry, rate limiter and the framework adapter (omitted with `--framework none`) |
| `.env.example`       | Documented template generated from the schema                                            |

and prints the install command for the packages the generated code imports, using your
package manager (detected from the lockfile).

If a `.env` or `.env.example` already exists, `init` **infers the schema from it**: variable
names, types (`url`, `port`, `number`, `boolean`, `enum`, `list`, `string`) and defaults are
guessed from the values and from NexKit metadata comments, so adopting NexKit in an existing
project starts from your real configuration. Review the result — inference is a starting
point.

Existing files are never overwritten without `--force`. `--dry-run` prints what would be
written.

### What `createNexkit()` gives you

<Tabs items={["Express", "Fastify"]} group="framework">
<Tab>

```ts
const kit = createNexkit({ isProduction, logger?, health?, rateLimiter?, bodyLimit? });
kit.logger;        // Logger (JSON in production, pretty otherwise)
kit.health;        // HealthRegistry — register your checks
kit.before(app);   // request context, secure headers, size limit, health routes, rate limit
kit.after(app);    // notFoundHandler + errorHandler
```

</Tab>
<Tab>

```ts
const kit = createNexkit({ isProduction, logger?, health?, rateLimiter? });
kit.logger;        // Logger
kit.health;        // HealthRegistry
kit.genReqId;      // pass to Fastify({ genReqId })
await kit.register(app); // registers the nexkit plugin with sensible options
```

</Tab>
</Tabs>

The generated file uses a `MemoryRateLimitStore` with a comment explaining that it is
single-process and how to swap in Redis. Replace it before running multiple instances.

## `nexkit doctor`

```bash
nexkit doctor
```

Checks and reports pass / warn / fail for:

- Node.js version ≥ 20;
- `"type": "module"` in `package.json`;
- `moduleResolution` is `NodeNext`/`Node16`/`Bundler` in `tsconfig.json`;
- installed `@nexkitjs/*` packages and whether their versions match;
- peer dependencies (`express` / `fastify`) present when the adapter is installed;
- `.env` is listed in `.gitignore`;
- `.env.example` exists.

Exit code is `1` when any check fails, so it can run in CI or a pre-commit hook.

## `nexkit generate config`

```bash
nexkit generate config [--out src/config/env.ts] [--from .env.example] [--example] [--force] [--dry-run]
```

Generates (or regenerates) the typed schema module. With `--from`, the schema is inferred
from an env file; with `--example`, `.env.example` is (re)generated from the schema in the
generated module's defaults. Run it after editing your schema to keep `.env.example`
current.

## `nexkit generate middleware`

```bash
nexkit generate middleware [--framework express|fastify] [--out src/nexkit.ts] [--no-health] [--no-ratelimit] [--force] [--dry-run]
```

Generates the wiring module alone. `--no-health` and `--no-ratelimit` drop those features
(and their imports) from the output.

## Global flags

`--help`, `--version`, `--force`, `--dry-run`. Usage errors exit with code `2`.

## Programmatic API

The CLI is also a library, useful for custom generators or tests:

```ts
import { run, renderEnvConfig, renderEnvExample, renderMiddleware, inferEnvFields, DEFAULT_ENV_FIELDS } from "@nexkitjs/cli";

const code = await run(["generate", "config", "--dry-run"], {
  cwd: process.cwd(),
  stdout: (line) => out.push(line),
  stderr: console.error,
});

const ts = renderEnvConfig(DEFAULT_ENV_FIELDS);
const fields = inferEnvFields(readFileSync(".env.example", "utf8"));
```

## How generated code is kept trustworthy

- Every template variant (Express/Fastify, with and without health/rate-limit) is rendered
  and **type-checked** in the CLI's test-suite.
- The repository's `examples/express-app` and `examples/fastify-app` are generated by the
  CLI; a test fails if the templates and the examples drift apart.
- Generated output is Prettier-stable, so formatting on save does not create noisy diffs.
