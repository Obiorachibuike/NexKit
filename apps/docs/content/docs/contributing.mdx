# Contributing

Thanks for your interest in NexKit. This page summarises how the repository is organised and
how to get a change merged; the canonical version is
[`CONTRIBUTING.md`](https://github.com/Obiorachibuike/NexKit/blob/main/CONTRIBUTING.md).

## Prerequisites

- Node.js **20 or newer** (CI tests 20, 22 and 24; `.nvmrc` pins 22).
- npm 10+ — the repo uses npm workspaces.

## Getting started

```bash
git clone https://github.com/Obiorachibuike/NexKit.git
cd NexKit
npm install
npm run build      # tsc -b over all packages in dependency order
npm test           # every Vitest project: packages + example apps
```

| Command                  | Purpose                                                              |
| ------------------------ | -------------------------------------------------------------------- |
| `npm run build`          | Type-check and emit `dist/` for every package                         |
| `npm test`               | All tests (package tests import siblings from source)                 |
| `npm run test:examples`  | Example apps only — they consume the built packages via `exports`     |
| `npm run verify:exports` | Check entry points, declarations and the documented export list       |
| `npm run verify:pack`    | `npm pack` every package, install tarballs into a fresh project, smoke test |
| `npm run lint`           | Type-aware ESLint                                                     |
| `npm run format`         | Prettier                                                              |
| `npm run check`          | lint + build + test + verify:exports (what CI runs)                   |
| `npm run build:docs`     | Build this website                                                    |
| `npm run dev --workspace apps/docs` | Run this website locally                                    |

## Repository layout

```
packages/      publishable @nexkitjs/* packages (core, errors, config, logger, health,
               response, ratelimit, express, fastify, testing, cli)
examples/      runnable Express and Fastify apps — also integration tests
apps/docs/     this documentation site (Next.js + MDX + Tailwind)
scripts/       verify-exports.mjs, smoke-pack.mjs, expected-exports.json
.changeset/    release notes for pending changes
```

Dependency direction is strictly **core → errors → everything else → adapters**. The core
package must never import a web framework.

## Making a change

1. Branch from `main`.
2. Write code **and tests**. Adapters have integration tests over real servers.
3. If you touch a CLI template, regenerate the example apps:

   ```bash
   npm run build
   (cd examples/express-app && node ../../packages/cli/dist/bin.js init --framework express --force)
   (cd examples/fastify-app && node ../../packages/cli/dist/bin.js init --framework fastify --force)
   ```

   A CLI test asserts the examples equal the template output.
4. If you add or remove a public export, update `scripts/expected-exports.json` (the
   verifier tells you exactly what changed) and the [API reference](/docs/api-reference/).
5. Add a changeset: `npm run changeset`.
6. Run `npm run check`.
7. Open a pull request. CI runs lint, build, tests on three Node versions, export
   verification, the pack smoke test and a docs build.

## Guidelines

- TypeScript `strict` with `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess`.
- ESM only; relative imports use explicit `.js` extensions.
- **No new runtime dependencies** without a clear justification. Packages currently have
  zero third-party runtime dependencies.
- Never log or throw raw secret values; anything that may contain user data goes through
  redaction or is marked non-exposed.
- Public APIs get JSDoc — it feeds the declarations and the docs.
- Document limitations honestly. If a feature only works in one process, say so in its name
  and its docs.

## Writing docs

Pages live in `apps/docs/content/docs/*.mdx` and are listed in `apps/docs/src/lib/nav.ts`.
Available MDX components: `<Callout type="note|tip|warning|danger">`, `<Tabs items=[…]
group="framework">` / `<Tab>`, and fenced code blocks with `title="file.ts"`. The search
index is rebuilt on every `dev`/`build`.
